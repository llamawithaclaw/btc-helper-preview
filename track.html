Evidence bundle provenance protocol

The latest read includes a public-safe evidence bundle with source timing, cadence-aware freshness, correction status, transformation version, and a content hash. The hash identifies the serialized record; it is not evidence that the model is correct or predictive.

  • Bundle ID and content hash
  • Decision timestamp and methodology version
  • Source as-of timestamp, retrieval timestamp, and expected frequency
  • Frequency-aware freshness and degraded/unavailable state
  • Transformation/schema version used for public normalization
  • Fallback, stale, imported, or manually reviewed status
  • Correction/revision status and provenance label

Benchmark specification

The benchmark program should compare equal-capital accumulation policies before BTC Helper makes timing claims.

  • Primary objective: compare disciplined accumulation behavior, not short-term price prediction.
  • Gap handling: degraded runs and missing publication dates must be visible and benchmark claims must be withheld or qualified.
  • Fixed DCA: ordinary recurring accumulation with the same public daily budget.
  • Seeded reserve: equal-capital reserve account available before the test window.
  • Reserve yield: optional cash/T-bill-style yield or cash-drag accounting for reserve balances.
  • Calendar deployment: equal-capital reserve deployed on fixed dates regardless of BTC Helper.
  • Simple drawdown rule: reserve deployed on mechanical drawdown triggers.
  • Valuation-only rule: reserve behavior driven by a single valuation-state proxy.
  • Matched random deployment: random reserve events matched to the observed number of BTC Helper reserve events.
  • Frozen BTC Helper policy: a locked public policy version evaluated prospectively before any methodology change.

Known limitations

  • Forward records have not yet observed reserve deployment or advanced baseline holds. That absence is tracked instead of tuned away.
  • Plan-translation changes do not always change scheduled-baseline behavior. Behavior-changing events are tracked separately.
  • The benchmark has not yet shown reserve-aware divergence from baseline DCA. That is a sample and context limitation, not a reason to tune the model for activity.
  • The latest public read now carries a public-safe evidence bundle. Older reads before bundle v1 remain partial and should not be treated as retroactive point-in-time captures.
  • Replayed cases are project-level audit artifacts, not a mature performance backtest or price-prediction proof.
  • Remaining replay candidates still need broader holder-behavior, leverage, and flow-context evidence before more of them can be counted as replayed.
  • Source-health labels describe public input completeness and freshness, not confidence that BTC price will rise.
  • Provider and source families are public; direct source links, exact series mappings, raw inputs, thresholds, weights, overrides, and calibration are not published.
  • Replay and historical cases remain separate from observed forward records.

Next validation priorities

  • Review prolonged Baseline only behavior and translation-change frequency without treating context changes as purchase changes.
  • Backfill holder-behavior evidence for remaining less-covered cases where source history exists.
  • Extend evidence-bundle coverage across future reads without backfilling false point-in-time provenance into older public records.
  • Expose normalized factor-state history where the public record supports it without disclosing thresholds, weights, or raw private inputs.
  • Track source-health degradation and recovery reasons over time.
  • Add prospective methodology-version boundaries before any benchmark behavior change.
  • Keep daily reads running even when users only need alerts on meaningful changes.

The detailed freshness page translates source domains, cadence, and known limitations without publishing raw metric values, thresholds, weights, or private calibration details.

Source-health rubric

  • Freshness: whether each source is current for its own expected cadence.
  • Coverage: whether required domains have enough public inputs to interpret the read.
  • Acquisition reliability: whether collection was direct, fallback, import-assisted, or unstable.
  • Transformation success: whether the public normalization step completed without exposing raw inputs.
  • Internal coherence: whether the source run had contradictions or warnings that limit usability.
  • Correction/revision state: whether a known correction, replacement, or timestamp review is attached to the run.
  • Substitution severity: whether missing inputs were replaced, softened, or withheld from benchmark language.

Factor-state history boundary

  • Current public factor states and directions can be shown when retained source-run history supports them.
  • Older daily permalinks may not reconstruct factor-level snapshots if the historical public record did not retain them.
  • Factor states are normalized public labels, not raw metric values or exposed thresholds.
  • Evidence-bundle v1 preserves the latest factor-state record with source timestamps and transformation version labels.
